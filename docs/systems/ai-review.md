# System: ai-review

Owner: builder-review. Folder: `src/main/services/review/`. Research: `research/tooling-and-stack.md` section 10.

## Purpose

Three graders behind one service: code review for build and refactor quests, breakdown grading, and explain-in-one-sentence grading. Three providers: Claude Code CLI (learner's subscription), Anthropic API (learner's key), tests-only (no AI).

## Providers

`IReviewProvider { id; status(refresh?); complete(request: { systemPrompt, userMessage, jsonSchema, signal? }): Promise<string> }`. The graders build prompts and parse JSON; providers only transport. `status()` answers a `ReviewProviderStatus` (available, reason, version) instead of a bare boolean so Settings can say why (A141).

- ClaudeCodeProvider: `claude -p --output-format json --json-schema <schema JSON> --system-prompt-file <prompt file> --tools "" --max-turns 1 --no-session-persistence --strict-mcp-config --setting-sources user`, user message on stdin, `cwd` a clean temp folder (empty; the prompt file sits beside it, A140), 3 minute timeout. Locate `claude` on PATH plus `~/.local/bin`, `~/.claude/local`, `/usr/local/bin`, `/opt/homebrew/bin`, `%USERPROFILE%\.local\bin`, `%APPDATA%\npm`. Record the CLI version at startup; if a flag is rejected, fall back to `--output-format text` and the tolerant parser.
- AnthropicApiProvider: `@anthropic-ai/sdk`, model from settings (default `claude-sonnet-5-5`), key from `safeStorage`, structured output through the same schema. Handles 429 with one retry after the stated wait, then surfaces the error.
- TestsOnlyProvider: deterministic; turns test results and the rubric into findings; explain items get "self-check against the model answer".

Selection: settings `auto` picks the first available in that order. An explicit choice that is not available falls back to tests-only with the reason (A142). Review is skipped when the build fails (the compiler already said what is wrong) and when the learner only pressed Run.

## Graders and schemas

Code review (`CodeReviewer`): system prompt = senior Unreal programmer mentoring; never writes the solution or more than one corrected line; cites file and line; judges correctness against the brief, the rubric line by line, Unreal conventions (UPROPERTY on every UObject pointer, TObjectPtr, delegate unbinding on EndPlay, no Tick where a timer or event fits, const correctness, forward declarations, header hygiene, quest-prefixed names), pattern use when the quest names one, naming, one-line comments. Output schema: `{ score 0..100, summary, rubric: [{ line, met: boolean, note }], findings: [{ severity: problem|suggestion|praise, title, detail, file?, line? }], reflectionQuestion, alternativeHint }`.

Breakdown grader (`BreakdownGrader`): input = spec, required pieces, reference plans, learner plan (pieces with purpose labels and edges), revision note. Rules: accept different valid splits; match labels by meaning; a required piece missing after revision is a hard fail; flag god classes, data owned by the wrong piece, missing events, wrong order; most of the score comes from the revision. Schema: `{ score, summary, requiredPiecesCovered: [{ label, covered, matchedTo? }], concerns[], strengths[], revisionQuality: 0..100, alternativeToShow: index }`.

Explain grader (`ExplainGrader`): one sentence from the learner against a model answer, graded on correctness, abstraction level (describes purpose, not line-by-line), and ambiguity. Schema: `{ score 0..100, verdict: correct|partly|incorrect, note }`. Always free for the learner.

Follow-up (`FindingExplainer`): "why is this a finding?" sends the finding and the code back for a plain-English explanation. Free, no XP effect, cached per finding.

## Done criteria

- Unit tests on recorded provider outputs for all three graders, including fenced and prose-wrapped JSON and a schema violation.
- One live run through Claude Code and one through the API logged in `docs/iterations.md` with the exact command line that worked and the CLI version.
- Prompts live in `src/main/services/review/prompts/*.md` and are versioned; a prompt change needs a note in `docs/decisions.md`.

## Architecture (keep current)

Last updated by M1.7c (review IPC, real graders behind progress, Submit orchestration).

### Folder `src/main/services/review/`
- `ReviewService.ts`: the one entry point. `reviewCode` (skips when the build failed), `gradeBreakdown`, `gradeExplain` (explain items and reflection answers), `explainFinding`, `getProviderStatuses` (cached checks), `testClaudeCode` (rechecks and sends a tiny real round trip, so "not signed in" shows in Settings; a not-installed or not-signed-in failure marks Claude Code in the selector, a timeout does not, a pass clears it). `createReviewService(settings)` builds the real parts. Each call asks the selector and runs the grader; what a failure does depends on its code:
  - `review-unavailable` or `secure-storage-unavailable`: the provider is marked and the selector asks again, so the review lands on the next AI provider in `auto` or on tests-only, which sets `fallbackReason` (A154, A301).
  - `review-timeout`: tests-only answers at once with `fallbackReason` and `retryReviewSuggested: true`; the next AI provider is never tried, so a slow Claude Code never becomes a paid API review, and the timed-out provider is not marked (A300).
  - cancel, refusal, invalid output, and anything else are thrown as they are.
- `ProviderSelector.ts`: reads `IReviewSettings.providerChoice()` on every call. `auto` walks Claude Code, then the API; anything unavailable ends in tests-only with the joined reasons. `markUnavailable(id, reason)` sets a provider aside for 10 minutes (`UNAVAILABLE_MARK_MS`, clock injectable); `statuses()` shows the mark's reason; `clearMark(id)` ends it.
- `ReviewInputs.ts`: what each grader reads (quest brief, rubric, files, `RunResult`; breakdown spec, required pieces, reference plans, both plans, revision note; explain prompt, model answer, context, sentence; finding plus files). Defined here until content types land (A148).
- `ReviewSchemas.ts`: zod schemas for each grader's model output (`provider` is added by the app, not asked of the model) and `toProviderJsonSchema`, which turns them into the JSON schema both providers receive: objects closed, enums kept, range keywords removed (A146).
- `reviewErrors.ts`: the AppErrors the service throws: `review-invalid-output`, `review-refused`, `review-unavailable`, `review-timeout`, `run-cancelled` (A143, A300).
- `parsing/extractJsonObject.ts`: tolerant extraction (bare, fenced, prose-wrapped, first balanced object, braces in strings skipped). `parsing/parseModelOutput.ts`: extraction plus a strict zod parse; any problem becomes `review-invalid-output` naming the grader and the first three schema issues, with the raw reply (trimmed) in `detail`.
- `prompts/*.md`: `code-review`, `breakdown-grader`, `explain-grader`, `finding-explainer`. Each starts with `<!-- prompt: <name>, version N -->`; `prompts/loadPrompt.ts` imports them with Vite's `?raw` (bundled into `out/main/index.js`), checks the header, and strips it (A150). A prompt change bumps its version and needs a note in `docs/decisions.md`.
- `graders/`: `CodeReviewer`, `BreakdownGrader`, `ExplainGrader`, `FindingExplainer` (in-memory cache by `<attemptId>:<findingIndex>`, 200 entries). After the schema parse they apply the checks in A144: rubric answer count must match and the quest's wording replaces the model's; every required piece must be answered and is put back in quest order; `alternativeToShow` must be in range; a cited file must exist and a cited line must be from 1 to the file's last line, or they are dropped (the schema accepts any integer, A159); fenced code longer than one line is replaced with a note (`limitCodeBlocks.ts`). `messageSections.ts` builds the tagged user message (files with line numbers, closing tags inside learner text broken so a file cannot end its section, A151).
- `providers/IReviewProvider.ts`: the transport contract. `providers/ClaudeCodeProvider.ts`: D11 flags exactly, with `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` removed from the spawned environment (A155); reads the `--output-format json` envelope (`structured_output` first, then `result` text); `stop_reason: "refusal"` is `review-refused`; `is_error` with "Not logged in" says to run `/login`; a timeout is `review-timeout` and a cancel is `run-cancelled`; if stderr says a flag is unknown it retries once with `--output-format text` and the schema appended to the system prompt, and stays in text mode. Requires CLI 2.1.275 or newer; version and path cached until `status(true)`. `providers/ClaudeCodeLocator.ts`: candidate paths per platform. `providers/IProcessRunner.ts` and `providers/NodeProcessRunner.ts`: spawn with stdin, timeout, and abort; stop is SIGINT, then SIGKILL after 5 seconds; on Windows a stop runs `taskkill /PID <pid> /T /F` without a shell to end the whole tree, and a `.cmd` shim runs through the shell with quoted arguments (A153, A157). The per-review temp folder is removed with retries and a cleanup failure never replaces the result.
- `providers/AnthropicApiProvider.ts`: `client.beta.messages.create` with the model from settings, `max_tokens` 16000, the system prompt cached (`cache_control: ephemeral`), and the schema as `output_config.format`. Adds the server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) for models that take it. SDK retries off; one retry on a 429 after `retry-after` (at most 60 seconds), none when the header is missing (the spend cap); a cancel ends the wait at once (A159). `refusal` is `review-refused`, `max_tokens` is `review-invalid-output`, a connection timeout is `review-timeout`, other SDK errors map to plain-English `review-unavailable` (A147, A300). A key that secure storage cannot read throws `secure-storage-unavailable` from the settings, which the service treats like an unavailable provider (A301).
- `providers/TestsOnlyProvider.ts`: not an `IReviewProvider` (it has nothing to transport); it answers each grader directly. Code: score is the share of tests passed, failed tests become problems, each rubric line becomes a "Self-check" suggestion, `rubric` is empty. Breakdown: required pieces matched by label (`labelMatches`): the learner label contains the whole required label, or its core (the label without kind words such as component, actor, event, data, step, system, manager and their plurals, and one-letter prefixes, see `KIND_WORDS` and `isKindWord`) is part of the required core, at least 4 characters long, and at least half the required core's length (A158, A302); alternative is the reference plan sharing the fewest labels. Explain: score 70, verdict `partly`, note "Self-check against the model answer: ..." (A145). Each answer carries `fallbackReason` and `retryReviewSuggested` when the service passes them.
- `settings/IReviewSettings.ts`: provider choice, model id, `hasApiKey`, `readApiKey()`. `settings/SafeStorageReviewSettings.ts`: reads the current settings through a closure and decrypts the key with an injected `safeStorage` only when a review needs it (A149).

### Wiring (M1.7c)
- `src/main/index.ts` builds the review service on first use from the settings service: `createReviewService(new SafeStorageReviewSettings({ currentSettings: () => settingsService.current(), loadEncryptedApiKey: () => settingsService.loadEncryptedApiKey(), decryptor: safeStorage }))`. The same instance answers the Title chip, the review methods, Submit, and the progress graders.
- Progress graders: `ProgressContentService` gets `{ gradeExplain, gradeBreakdown }` that call the review service, so `reviseBreakdown` and explain drill items are graded by Claude Code or the API, with the service's own tests-only fallback. This replaces the A318 stand-in (A460).
- `createReviewHandlers.ts` builds the five handler calls the IPC layer takes through `HandlerDependencies.getReviewHandlers()`:
  - `getReviewProviders` and `testClaudeCode` go straight to the review service.
  - `explainFinding` and `answerReflection` go through `AttemptReviewService.ts`, which finds the attempt in `PlayerProgress.attempts` by id, reads its stored `review`, and answers `attempt-not-found` when the attempt, its review, or the finding is missing (A464). The finding explanation is cached as `<attemptId>:<findingIndex>`; the reflection answer is graded by the explain grader with the review's question as the prompt and its summary as context. Both are free and change nothing in progress.
  - `submitQuest` runs inside `trackRun` (run id, cancel, stamped progress) through `QuestSubmitService.ts`: look up the authored quest (build or refactor only, A461), run it through the runner, send a `reviewing` progress step, review the code (`codeReviewInputFrom.ts` maps the quest's title, brief, rubric, and pattern ids to card titles), then record through `CodeAttemptRecorder.ts`. The recorder scores with `PassRules` (0.6 tests plus 0.4 review; a tests-only review counts as no review score, so the score is the tests, A462) and calls `ProgressService.recordAttempt` with `isSubmit: true`. A cancel between steps throws `run-cancelled` and records nothing.
- Every Submit attempt stores its code review and its files on the attempt record (A466, A467: files capped at 64 KB each and 256 KB per attempt, kept on the quest's last five Submits). The follow-ups read the review and those files, never the quest's draft.
- The run step is `QuestRunService.runQuest` from `createUnrealServices`, the same path the `runQuest` handler uses: prerequisite fill from reference solutions (A65), file writing, the runner, and its progress events. `index.ts` passes it to `createReviewHandlers`, so every Submit dependency is built in the composition root (A468).
- Engine check: `tests/integration/submitQuest.test.ts` (opt in with `DOJO_ENGINE_ROOT`) creates a sandbox and submits a Pack 1 World 1 quest through the real `submitQuest` handler with the tests-only reviewer (A469).
