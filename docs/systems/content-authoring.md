# System: content-authoring

Owners: author-foundations (Pack 1), author-patterns (Pack 2), author-mechanics (Pack 3), author-systems (Pack 4). Folder: `content/`, `tools/solutions/`. Read before writing anything: `research/gamedevtv-exercise-design.md` (sections 3, 6, 7), `research/patterns-inventory.md` (the pattern you are writing, Part 3 order, Part 4 bosses), `research/gamified-learning-platforms.md` section 3, `research/unreal-concepts-inventory.md`, and `docs/product.md`.

## Non-negotiables

- Original wording and code. Sources give structure and concepts, never text, names, numbers, or example strings.
- Valid UE 5.8 C++: CoreMinimal first, the right base header, `.generated.h` last, GENERATED_BODY, real specifiers, correct delegate signatures, UPROPERTY on every UObject pointer, TObjectPtr, forward declarations in headers, quest-prefixed class names (`ADojoM3PressurePlate`), no `MODULE_API` macro.
- Every build and refactor quest ships a reference solution in `tools/solutions/<quest-id>/` and automation tests that the verifier compiles and runs with `--engine`. The starter must not already pass.
- Every quest lists `terms[]` that exist in the glossary and `prerequisites[]` that exist. New terms go into `content/glossary.json` in the same task, with an Epic docs link.
- No em dashes anywhere.

## Author rules (from `research/gamedevtv-exercise-design.md` section 7, adopted in full)

One sentence naming the finished behavior opens every build quest. One new idea per quest. An exact observable for verification, asserted by the test and seen in the editor. Ramp inside the quest (naive then better, with the reason). One deliberate failure per world, revealed only after the step that fails. Rubric and concepts shown beside the brief state outcomes only, never the deliberate failure or its fix; the reasoning goes in the text shown after a pass. Experiments are A/B on one setting and become a recall question. Hints are a ladder of three with no code. Name the pattern right after it is built, never before. State the dependency direction in every two-actor quest and put it in the rubric. Reuse on purpose from world 3 on. Model conventions in starters. Bosses have fixed numbers, a named reference game, three extensions in order of importance, and a feel criterion. Mechanic and system quests start with a breakdown with at least two reference plans. Difficulty, time estimate, and a 5 to 6 bullet rubric (8 for bosses). Teach tooling in the world that needs it. Supply widgets when a quest needs UI. 

## Learning-science rules (from the platforms research)

Predict question before every concept card. Scaffold fades inside each world: worked, faded, stub, blank (the verifier checks). Worked-level quests mark 3 to 5 lines for the self-explanation gate. Each world has a Parsons block for at least two of its functions with one or two Unreal distractor lines. One explain-in-one-sentence item per concept quest with a model answer. One alternative with a tradeoff note per build quest. Breakdown pieces carry purpose labels; reference plans label every piece.

## File formats

One complete example per kind lives in `content/examples/` (concept, breakdown, build at each scaffold level, refactor, boss) and parses under the verifier; copy from those:

- `01-concept-uproperty.md`: concept, with every question type.
- `02-build-worked-lantern.md`: build at worked level, with `// @explain:` marked lines and two Parsons blocks.
- `03-build-faded-flicker.md`, `04-build-stub-lantern-switch.md`, `05-build-blank-proximity-lantern.md`: build at faded, stub, and blank.
- `06-refactor-lantern-tick.md`: refactor.
- `07-breakdown-campfire.md`: breakdown with two reference plans.
- `08-boss-lighthouse.md`: boss with build pieces and an 8 bullet integration rubric.

The five code examples ship reference solutions in `tools/solutions/example-*/` and pass `npx tsx tools/verify-content.ts --engine ~/Applications/UE_5.8` (A207): each solution builds and passes its tests, and each starter does not. Their tests use the sandbox's `FDojoTestWorld` and include quest headers as `Quests/<quest-id>/<File>.h`, the folder QuestFileWriter writes to; a quest's own `.cpp` includes its own header by bare name. Copy that include form. Section order per kind, the front matter fields, and every data shape are in `docs/systems/content-engine.md` under "Markdown format". Run `npx tsx tools/verify-content.ts --quest <id>` to check one quest while writing it. A world id must be unique across every pack, not only inside yours (A73): pick ids that cannot collide with another pack's worlds, and the verifier fails on a world id another pack already uses.

Includes in real quests (A260): the sandbox puts quest files in `Source/Dojo/Quests/<quest-id>/` and tests in `Source/Dojo/Tests/`, and only the module root is on the include path, so tests and any quest that reuses an earlier quest's class include `"Quests/<quest-id>/<File>.h"`. A file includes its own header by bare name. Pack 1 uses quest ids `f1-<slug>` to `f6-<slug>`, classes `ADojoF<world><Name>`, and test names `Dojo.F<world>.<Quest>.<Case>` (A261).

Boss solution layout (A67, A340): `tools/solutions/<boss-id>/` holds the boss's own integration code (`.h` and `.cpp`, written to `Source/Dojo/Quests/<boss-id>/`) and `<boss-id>.Test.cpp` with its two-round tests. When the boss adds functions to earlier classes, it ships extended copies of those piece files in `<piece-quest-id>/` subfolders, named after one of its `pieces` and using that piece's own file names; at build time they replace the piece's files, and the piece's own tests run against them to prove the additions changed no rules.

### Glossary entries (`content/glossary.json`)

Ids are kebab-case (`actor-component`). `short` is one sentence ending in a period, for the hover card. `long` is one paragraph in our own words. `unrealDocsUrl` is locale-free and pinned to the engine version: `https://dev.epicgames.com/documentation/unreal-engine/<path>?application_version=5.8`. API links use 5.8's flat paths (`API/Runtime/<Module>/<Symbol>`). Every `related` id must exist in the file. `category` is a display label copied exactly from the existing set (mostly lowercase words such as `framework` or `object model`; acronyms such as `AI` and `UI` stay uppercase); reuse one before adding a new one. Leave `firstQuestId` out until the quest exists. Set `linkMode: "code-only"` on any entry whose term is also an everyday English word (`check`, `ensure`, `Cast`, `Destroy`, `Category`, `Super`), so it links only inside inline code (A62). Aliases must be specific to the entry: never a bare English or C++ keyword such as `override`, `virtual`, `assert`, or `Remove`.

How terms link in quest text (A200, A62): the app turns glossary terms into hover links in prose, longest match first, matching identifiers such as `AActor` exactly and plain words such as "actor" in any case; headings, code blocks, and links are never linked. Normal terms also link inside inline code, but only when the whole code span is one term or alias, so `` `AActor` `` and `` `BeginPlay()` `` link while `` `AActor* Owner` `` does not. A `linkMode: "code-only"` entry (`check`, `ensure`, `cast`, `destroy`, `category`, `super`) links only that way, never in prose, so write those terms in backticks when you want a hover card.

### Drill items (pattern `recall[]` and `scenarios[]`, concept `questions[]`)

Every item has `id` (kebab-case, unique within its quest or pattern card; pattern items use `<pattern-id>-recall-<n>` and `<pattern-id>-scenario-<n>`), `type`, `prompt`, and `explanation` (shown after answering). Extra fields per type:

- `multiple-choice`: `choices[]` (3 or more, distinct), `answerIndex` (0-based).
- `fill-blank`: `prompt` holds exactly one `___`; `acceptedAnswers[]` lists every spelling that counts as correct.
- `which-pattern`: `choices[]` are pattern ids from `content/patterns.json`, `answer` is one of them, `distractorNotes[]` is `{ choice, why }` for every wrong choice (why it looks right and why it is not).
- `spot-the-bug`: `code` (C++ snippet, no leading or trailing blank line), `bugLine` (1-based line in `code`), `fix` (one sentence, no code dump).
- `explain-in-one-sentence`: `modelAnswer`, `rubric[]` (the points a learner's sentence must hit).

Spot-the-bug code has exactly one wrong line; a missing line is not a bug line, so write the code so the mistake sits on a line that is present. Spread `answerIndex` across positions (the drill runner also shuffles, A61). Intents and every other card field are written from scratch around an Unreal example, never as a rewording of a book or Gang of Four intent line.

Pattern cards list ids in Part 3 teaching order, with Strategy, Factory Method (`factory-method`), and Facade after the 19 book patterns. Scenarios are mostly `which-pattern`; a scenario may answer a neighboring pattern to sharpen the contrast, and a "when not" scenario is written as `multiple-choice`, never as a which-pattern item whose answer is the pattern to avoid.

## Pack briefs

Pack 1, Unreal C++ Foundations: worlds and topics in `docs/product.md`. Use `research/unreal-concepts-inventory.md` for the concept order and glossary ids. World 1 is the vertical slice: 6 concept quests, 4 build quests on the fade ladder, the "dash with cooldown" breakdown from the GameDev.tv research section 6, one boss.

Pack 2, Patterns in Unreal: follow `research/patterns-inventory.md` Part 3 order exactly; each pattern gets the mini-arc (predict and card from the chapter study, recognize items from its recall and scenario questions, two build use cases from its use-case list in different mechanics, one refactor, one when-not item); combos world uses Part 4 bosses. Lesson zero is the architecture chapter as a concept quest. World 1 (`01-lens-and-observer`) holds lesson zero and the Observer arc, so Observer comes before the Time world (A370); quest ids are `p<world>-<slug>`, classes `ADojoP<world><Name>`, tests `Dojo.P<world>.<Quest>.<Case>` (A372). World 2 (`02-time`) holds the Game Loop arc (A472). From World 3 (`03-update-method`) on, each pattern arc is its own world in Part 3 order (A491).

Pack 2 World 18 (`18-spatial-partition`, world id `spatial-partition`, A1691) is Spatial Partition: seven quests ending in the boss `p18-boss-moth-meadow`. Every grid in it is for things the physics scene cannot see (lanterns with no collision, moths kept as structs), and every quest that builds one says when an overlap query or an overlap event is the better answer (A1695). Grids work on the ground plane with `FMath::FloorToInt32` cells, and every query reports how many things it measured, which the tests bound (A1696, A1697). Later quests that need a grid of actors reuse `FDojoP18Grid` (`Quests/p18-lantern-grid/DojoP18Grid.h`), and those that need many cheap agents reuse `ADojoP18MothSwarm` (`Quests/p18-moth-swarm/DojoP18MothSwarm.h`), listing those quests under "Compiles against earlier quests:" and in prerequisites.

Pack 3, Mechanics Lab: the 8 modules with the 96 original exercise ideas and 16 bosses from the GameDev.tv research section 6, pruned to 4 to 6 build quests per world plus breakdowns of the 15 ready mechanics. World 6 boss is the Quest System (two reference breakdowns, pieces, integration rubric with 8 bullets, difficulty 5). Naming (A870): world folders keep their pack position (World 6 is `06-delegates` even while Worlds 1 to 5 are unwritten), quest ids are `m<world>-<slug>`, classes `ADojoM<world><Name>`, and tests `Dojo.M<world>.<Quest>.<Case>`.

Pack 3 World 1 (`01-input`, world id `input`, A1110) is Enhanced Input: ten quests, ending in the boss `m1-boss-drone-handoff`. Any later quest that needs a pressed key uses the test rig `FDojoM1InputRig` (`Quests/m1-turntable/DojoM1InputRig.h`, A1113). It gives the test world a game instance, a local player, and a player controller; `Possess` runs the engine's own possession path; `Press` and `Release` send simulated key events; and `Rig.Tick` replaces `FDojoTestWorld::Tick`, because only the engine loop ticks the Enhanced Input module that applies changed mapping contexts. A quest that includes the rig lists `m1-turntable` under "Compiles against earlier quests:" and in its prerequisites. A pawn made in code needs a scene root (`RootComponent`) or it has no place in the world, and a pawn destroyed while possessed destroys a controller that has no player state, so release it first.

Pack 3 World 3 (`03-collision`, world id `collision`, A1331) is collision: ten quests ending in the boss `m3-boss-vault-room`. Later quests that need a player stand-in or a crate reuse `ADojoM3Runner` (`Quests/m3-checkpoint/DojoM3Runner.h`, a plain actor whose root sphere has the Pawn profile, with a respawn point) and `ADojoM3Crate` (`Quests/m3-scale-plate/DojoM3Crate.h`, a solid body and an overlapping handle, with a home), listing those quests under "Compiles against earlier quests:" and in prerequisites (A1334). Collision tests move shapes by teleport (`SetActorLocation`, which updates overlaps) or by sweep, never by physics simulation (A1338).

Pack 3 World 4 (`04-spawning`, world id `spawning`, A1401) is spawning and timers: ten quests ending in the boss `m4-boss-fuse-yard`. Later quests that need a timed bomb reuse `ADojoM4Bomb` (`Quests/m4-fuse/DojoM4Bomb.h`: `Light` only ever brings a burning fuse forward, `StartFuse` lights it at BeginPlay when set before FinishSpawning). Randomness in quests goes through a seeded `FRandomStream`, and tests check properties or compute the expected result from the actual layout (A1403).

Pack 3 World 5 (`05-tracing`, world id `tracing`, A1480) is tracing: ten quests, ending in the boss `m5-boss-watchtower` (two sentries, a pillar, and a laser fence, with an awareness meter). Quest ids are `m5-<slug>` (the file names keep the build number, the ids do not), classes `ADojoM5*`, tests `Dojo.M5.<Quest>.<Case>`. Its tests build their own solid boxes and a character-like capsule, tick one frame after every change to the scene before they query it, and read numbers (distances, stop locations, path points, meter values). The build quests fade worked, faded, faded, stub, blank; the deliberate failure is the sentry's eye, whose hero capsule ignores the Visibility channel. The boss uses the sight and laser pieces; the feeler is its first extension.

Pack 3 World 8 (`08-gameplay-moment`, world id `gameplay-moment`, A1602) is the last Mechanics Lab world: a breakdown of a written walkthrough, two method cards, five builds, and the boss `m8-boss-blackout-escape` (A1939 to A1945: the quest 8 clock is a true blank and its starter names no guard, and quest 1 now requires the Pack 3 World 4 and World 5 bosses). Its pieces keep their listeners as small provided actors (`ADojoM8SightLog`, `ADojoM8PowerLog`, `ADojoM8EscapeLog`, `ADojoM8AlertLog`) so tests can count announcements, and its tests use World 3's runner as the hero stand-in; the boss plays the real World 1 walker through the World 1 rig, with a collision ball the director gives it in code (A1603). A world that needs a hero with a shape can do the same. The searchlight's tracing is used, not taught, until Pack 3 World 5 lands (A1601).

Pack 4, Systems Lab: the 8 systems specced in the GameDev.tv research section 6, each a boss-shaped world (breakdown, pieces, integration) naming the patterns it combines. The pack id is `systems` with `order: 4`, which is what `PACK_GATES` in `rules.ts` keys on. Naming (A1150): world folders are `<nn>-<world-id>` with the world's own position (World 1 is `01-inventory-and-equipment`), quest ids are `s<world>-<slug>`, classes `ADojoS<world><Name>`, and tests `Dojo.S<world>.<Quest>.<Case>`. Later worlds may require the previous world's boss instead (World 4 requires `s1-boss-expedition-pack`, which already requires the gate bosses and the pattern worlds). Each world opens with a breakdown whose prerequisites are the Pack 1 Communication boss and the Pack 2 Component boss (the first quest of a pack is always available once its gate opens, so prerequisites on it only record the gate), and its first build lists the last quests of the Pack 2 worlds that teach the other patterns the world combines; the pieces climb the fade ladder; the boss integrates them with a director that owns no rules.

Pack 4 World 2 is the ability system (`02-ability-system`, world id `ability-system`, A1350); the research's next system, the Quest System, is Pack 3 World 6's boss. A world that needs gameplay tags declares them as native tags in a namespaced header (`UE_DECLARE_GAMEPLAY_TAG_EXTERN` inside `namespace DojoS2Tags`) and defines them in one `.cpp` with `UE_DEFINE_GAMEPLAY_TAG_COMMENT`, so no sandbox config is needed (A1353); tag names start with the world prefix (`DojoS2.State.Rooted`) because every quest compiles into one module. A world may add concept quests when it is the first to teach an Unreal feature (A1351).

Pack 4 World 6 (`06-ai-perception-and-behavior`, world id `ai-perception-and-behavior`, A1560 to A1565, and A1891) has eight quests: two concept quests, `s6-senses-blackboard` before the first build and `s6-tree-nodes` before the walk beat, teach the eight AI terms, and the decorator is taught as a gate only until the clue quest. It is AI with a Behavior Tree and Blackboard (State Tree needs plugins the sandbox does not enable). A headless test has no tree assets, so trees are built in code with `FDojoS6TreeKit` (`Quests/s6-walk-beat/DojoS6TreeKit.h`), which also names the guard's four blackboard keys; `FDojoS6TreeKit::Run` starts a tree on a pawn's AI controller. `FDojoTestWorld` makes a game world with no AI system, so every World 6 test calls `FDojoS6TreeKit::EnableAI` first; without it no tree starts and perception is silent. Later quests that need a guard reuse `ADojoS6Guard` (`Quests/s6-walk-beat/DojoS6Guard.h`, a pawn with a beat that an AI controller possesses as soon as it spawns) and list `s6-walk-beat` under "Compiles against earlier quests:" and in prerequisites. Tasks move the pawn with `SetActorLocation` from `TickTask`, because the test world has no nav mesh (A1562). Tests reach perception by broadcasting `OnTargetPerceptionUpdated` with `FAIStimulus` values after `RegisterSenseClass`, and the boss uses real sight and hearing (A1563).

Pack 4 World 3 is save and load (`03-save-and-load`, world id `save-and-load`, A1420). Tests that write save slots use a slot name unique to the test and delete it at the start and the end, because every test in the sandbox shares one `Saved/SaveGames` folder.

## Done criteria per world

Verifier green with `--engine` on the Windows desktop (or logged as unverified on the Mac); a fresh reviewer agent spot-check for copied wording, solution leaks, UE API accuracy, and the fade ladder; an `iterations.md` entry listing the quests and their observables.

Bosses (A67): every boss ships a C++ reference integration of one of its reference plans in `tools/solutions/<boss-id>/`, with automation tests that drive simulated time through two full rounds and assert the observables named in the spec. The verifier builds and runs it with `--engine`. Layout (A215): the folder's `*.Test.cpp` files are the tests and every other `.h` and `.cpp` file is integration code; a subfolder named after one of the boss's `pieces` holds extended versions of that piece's files (same names only), which replace them while the boss is built; nothing else goes in the folder. An include of a piece quest's files needs the A268 line in the spec.
